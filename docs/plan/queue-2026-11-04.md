### CH-04 claude.ai export importer

Input.

Zip handling. Treat every byte as untrusted.

- Enforce configurable limits. Proposed defaults are 10 GB total uncompressed, a 200 to 1 compression ratio per entry, 100,000 entries and a nested zip depth of 2.

Layout detection.

- Support the three layouts in report section 7.2. These are the single zip, the per-project files layout and the manifest plus category zips layout.

Parsing.

- Unified Claude chats that continued in the cloud appear as tool_use and tool_result blocks (report section 1.2). Render them as cloud steps.

- The export does not link conversations to projects. Do not guess. Show imported projects separately and let me link conversations by hand.

Untrusted instructions.

Re-import.

- Key on source uuid. Skip unchanged records. A record with a newer `updated_at` replaces the imported snapshot. Forks keep their link through the source uuid and never change.

Redaction and audit.

- Run the existing redaction pipeline before storage. Record redaction counts per message and show a marker in the viewer.

Fixtures.

- Build a fixture generator for all three layouts from the report's examples. Include malformed, truncated, unknown-field, two-root and zip attack variants, plus a synthetic 1 GB single-line `conversations.json`.
- Never commit real export data.

**Done when**

### Export format (observed, undocumented, unstable)

Layouts by era:
- 2024 to mid-2026: conversations.json, projects.json, users.json.
- Aug 2026: conversations.json, projects/<uuid>.json (one per project), users.json, memories.json.
- Oct to Nov 2026: a manifest JSON plus one zip per category, e.g. conversations-000.zip containing conversations.json, projects-000.zip (one JSON per project); categories reported include design_chats, frames (artifact versions), projects and memories. Low confidence.

conversations.json: one JSON array, often minified, can be about 1 GB on one line, non-ASCII escaped. Conversation fields: uuid, name (may be empty), summary (often empty), created_at, updated_at (ISO 8601 UTC, e.g. 2026-02-24T15:30:05.650472Z), account { uuid }, chat_messages[]. No project_uuid: the export does not link conversations to projects.

Message fields: uuid, sender ("human" or "assistant", not role), text (flattened; thinking and tool blocks replaced by a placeholder, so use content), content[] blocks, created_at, updated_at, attachments[], files[], parent_message_uuid (tree; root parent is 00000000-0000-4000-8000-000000000000). Branches: siblings under one parent, no active-leaf marker, some conversations have two roots; follow the latest created_at child at each fork (heuristic).

Content block types: text (text, sometimes citations, start_timestamp, stop_timestamp); thinking (thinking, key not confirmed); tool_use (id, name, input, integration_name, mcp_server_url, timestamps; artifacts appear here as tool calls); tool_result (tool_use_id, content, is_error); image and document (file_uuid only); injected_prompt_block (injection_source such as memory_block_head, date_note); token_budget and flag (internal markers).

attachments[]: file_name, file_size, file_type, extracted_content. files[]: file_name plus a UUID key, probably file_uuid (not confirmed).

# A chat's outputs folder (Chat build, deferred from CH-03 by ADR 0012)

Let a chat write files into its own `outputs` folder, and nowhere else. First the engine needs workspace roots scoped to one session (the chat's own outputs folder, for that chat's calls only), because chat folders are outside the workspace roots and `outside-workspace-write` denies every write there; then an allow rule `chat-outputs-write` (Write and Edit, `sessionKinds: [chat]`, inside that folder only), with tests that a chat cannot write into another chat's folder, Codehouse's data or a project, and that a coding session gains nothing.
