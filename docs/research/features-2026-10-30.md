# JCVC feature research. Best features of coding agent interfaces

Prepared 30 October 2026 for the JCVC build session, from the brief in `feature-research-prompt.md`. Saved as returned.

Live documentation pages were retrieved on 30 October 2026. Every claim carries a source ID. The source list at the end gives the link, the date and the source type. Sources older than six months (before 30 April 2026) are marked **older**. Preview, beta and research-preview features are marked as such.

Evidence labels used throughout

- **Doc** means vendor documentation, changelog or release notes (primary).
- **Research** means peer-reviewed or vendor research paper.
- **User** means user opinion from issues, forums, blogs or reviews. Treat as signal, not fact.
- **Unk** means not verified in this research. Absence of evidence is not evidence of absence.

## Summary

### Situation

- The Claude desktop Code tab now ships most of the table-stakes workbench features JCVC lacks today. These include an integrated terminal, worktrees, diff line comments, PR and CI monitoring, scheduled tasks, session archive and grouping, a context meter and side chats. [S1][S2]
- In 2026 every major tool added a model-based reviewer for approvals. Claude has Auto mode, Codex has auto-review, VS Code has Assisted permissions, Cursor has an Auto-review run mode. [S1][S17][S22][S29]
- None of the reviewed tools presents its permission policy to a non-technical user in plain language. Policy is exposed as modes, settings keys or TOML and JSON files. [S1][S15][S22][S42]
- Non-developer tools compete on starting from one prompt, live preview and one-click rollback. They mostly avoid permission questions by running in hosted sandboxes. [S31][S33][S36][S38]

### Key findings

- JCVC's differentiators are the Approver with a never-allowed floor, a hash-chained audit of every decision, a global kill switch and approvals over desktop, iPhone, ntfy and Slack. No reviewed tool documents a tamper-evident audit of every decision or a kill switch across all sessions. (Based on docs reviewed.)
- Parity gaps with the highest user value are diff review with keep or undo and line comments, a visible message queue with steering, session management, worktrees and a terminal pane.
- The largest opportunity is a policy studio grounded in permission research. The research points to deciding by reversibility, short-lived grants, a learning period before enforcement, rare and varied prompts, and an explanation for every decision. [S47][S48][S50][S53][S55]
- Undo in Claude Code and VS Code does not cover shell side effects. Checkpoints track only edits made through file tools. [S4][S24] JCVC can close this gap by snapshotting before risky shell commands.

### Risks and assumptions

- Many 2026 comparisons are vendor blogs or aggregators of Reddit and Hacker News comments. They are labelled User and used only as signal.
- Lovable evidence is from April 2025 (**older**). Lovable's 2026 feature set was not verified.
- Firebase Studio is being shut down (new signups disabled 22 June 2026, shutdown planned 22 March 2027). [S39] Its blueprint pattern is still the best evidence for naming a project from the first prompt.
- Crystal was deprecated in February 2026 and the company behind Vibe Kanban shut down in April 2026. [S44][S45] Windsurf was renamed Devin Desktop on 2 June 2026. [S46]
- Assumption. JCVC can launch a local browser and child processes on the managed laptop, and git is available. Worktrees, PR flow and preview self-checks depend on this.
- Assumption. A default projects folder under Documents may be redirected to OneDrive on a corporate laptop. Syncing `node_modules` through OneDrive is slow and noisy. Confirm the path policy before building item F7.

### Recommended actions

1. Build Policy Studio v2 with presets, example-based rule cards, grant lifetimes and a decision explanation line (F1, F2, F4). Priority 1. Owner is the JCVC build session.
2. Add Watch mode (learning period) and rule suggestions on top of the existing audit log and insights (F3). Priority 1.
3. Add reversibility-aware approvals with a pre-command snapshot for risky shell commands (F5). Priority 1. This is the one safety feature no reviewed tool documents.
4. Close the review gap with a diff pane that supports hunk keep or undo and batched line comments (F6). Priority 2.
5. Ship the beginner start flow. Default projects folder, blueprint card from the first prompt, automatic git init and first checkpoint (F7, F8). Priority 2.
6. Confirm with IT, before building, whether `gh`, git worktrees and a local browser automation channel are permitted. Items F13, F20, F24 depend on it.

## C. Ideas for non-technical users

### C1. Starting a project

- Firebase Studio's App Prototyping agent turns the first prompt into a blueprint with a proposed app name, required features and style guidelines, then starts coding. [S38] The product is being shut down but the flow is the clearest model for naming from the first prompt. [S39]
- Replit Agent offers two starts, build the full app or start with a design, plus an option to keep planning before building. [S31] Its plan shows what and why, what done looks like, what is out of scope and numbered steps. [S32]
- The Claude desktop Code tab asks the user to pick environment, folder, permission mode and model before the first message. [S1] It pre-creates up to eight environments from the user's most used folders. [S1] This works for developers and is friction for a beginner with no folder yet.
- Codex chooses defaults by folder type. A version-controlled folder starts in Auto (workspace write with on-request approvals) and a folder without version control starts read-only. [S15] Implication for JCVC. Always initialise git for new projects so JCVC can safely offer more autonomy.

Recommended flow for JCVC

1. User types the idea on the home screen. No folder picker.
2. JCVC shows a blueprint card. Name, one-line purpose, 3 to 5 features, look and feel, and the stack chosen for them in plain words ("a web page that runs in your browser").
3. User edits or confirms. JCVC creates the folder in the default projects folder from a short slug of the name, runs `git init`, writes a first checkpoint called "Project created" and opens the session in Plan mode.
4. The path is shown once in plain language ("Your project is saved in ...") with an Open in Explorer button.

### C2. Naming and placing

- Use the blueprint name as the display name and a short ASCII slug as the folder name. Append a number on collision. (Engineering judgement, not sourced.)
- Allow rename while no session is running. Rename the folder and update the session index together.
- Confirm whether Documents is redirected to OneDrive on the managed laptop before choosing the default location (see Risks).

### C3. Previews

- Claude desktop's Browser pane starts the dev server automatically, verifies changes after each edit by default, lets the user select an element, uses a clean browser profile separate from the personal browser and asks per site before acting on external pages. [S1]
- Replit App Testing drives a real browser like a user would and provides video replays of each test session. [S31]
- Lovable visual edits and Cursor Design Mode let the user point at an element and change it. [S34][S30]
- Bolt's preview runs inside the browser, and a third-party analysis warns that apps can work in preview and fail after deploy because missing secrets and settings were supplied by the preview. [S69] (User)
- For JCVC. Add a "Check my app" step that runs inside an in-process SDK tool (stdio and http MCP are blocked), captures a screenshot and console errors into the transcript, and links the screenshot to the checkpoint.

### C4. Explaining what happened

- Lovable's Chat Mode agent answers questions, plans and debugs without editing code. [S34] Bolt's Discussion Mode uses about 90 percent fewer tokens than Build Mode. [S36]
- Codex now explains safety blocks and offers safer follow-up prompts to choose from (29 October 2026). [S14] It also gives recovery guidance when an action needs approval that the chat's permissions cannot request (8 October 2026). [S14]
- VS Code shows a notice whenever a tool or command is auto-approved, with a link to the setting that allowed it. [S22]
- Claude desktop offers Normal, Thinking and Verbose transcript views. [S1]
- For JCVC. End each turn with a plain-language summary card. What changed (files, in words), what ran (commands, in words), what was blocked or asked, how to check it (open preview, click X), and the checkpoint to go back to.

### C5. Recovering from mistakes

- Replit checkpoints capture project files, AI conversation context and connected databases, appear as git commits, and allow rollback to any point. [S33] The docs also describe comparing how the app looked at different checkpoints. [S72]
- Claude Code `/rewind` restores code, conversation or both. [S4] It does not track files changed by shell commands such as `rm`, `mv` or `cp`. [S4] VS Code checkpoints do not reverse terminal commands, network requests or deployments. [S24]
- Bolt automatically attempts one fix when an error occurs and warns that repeated Attempt fix clicks waste tokens. [S36] Its preview troubleshooting asks users to paste the exact terminal error rather than a general complaint, and to diagnose in Plan mode. [S37]
- For JCVC. A "Go back to when it worked" timeline of checkpoints with a screenshot and one-line description each, and a "Fix this error" button that captures the exact error, tries once, then switches to Plan mode with an explanation instead of looping.

### C6. Keeping people safe without technical questions

- Claude desktop's browser will not purchase items, create accounts or bypass CAPTCHAs without the user's input, even on an approved site. [S1]
- Lovable runs a security scan when the user publishes, if a Supabase backend is connected (April 2025, **older**). [S34]
- Little Snitch recommends its silent, allow-and-record mode to new users for the first week, then a review of what happened before switching to alerts. [S53]
- For JCVC. Default beginners to the Balanced preset, run Watch mode for the first sessions, and phrase every question as a consequence ("This will publish your code to GitHub. Others may see it.") rather than as a command.

## D. Permission and policy design for ordinary people

### D1. What the research and consumer products show

| # | Finding | Source | Implication for JCVC |
|---|---|---|---|
| 1 | Permission mechanisms should be chosen in order of attention cost. Automatic grant, then trusted UI tied to a user action, then runtime dialogs, then install-time warnings. Automatic grant fits only reversible or low-severity permissions and should come with auditing and a way to revert. | S47 (Research, **older**) | Make in-project edits reversible with checkpoints, then auto-allow them with an audit entry |
| 2 | In that analysis of 76 platform-neutral permissions, about 60 percent could be granted automatically, 21 percent through trusted UI, 11 percent needed runtime dialogs and 7 percent install-time warnings. | S66 (Research, **older**) | Most agent actions should never produce a prompt |
| 3 | Attention to repeated warnings drops sharply across a workweek with only partial overnight recovery. Warnings that change appearance (polymorphic) sustained attention. In a three-week field study, adherence fell for standard warnings and stayed higher for polymorphic ones. | S48 S49 (Research, **older**) | Keep prompts rare and vary their design by risk tier |
| 4 | Chrome automatically moves users who repeatedly deny notification prompts, and sites with very low acceptance, to a quieter prompt. A large experiment found this cut unwanted interruptions with only a marginal effect on grant rates. | S50 S51 (Doc and Research, **older**) | Use decision history to quiet prompts the user always answers the same way |
| 5 | Android offers "Only this time" for location, microphone and camera, auto-resets permissions of apps unused for months, and stops showing a prompt after the user denies twice. | S57 (Doc, **older**) | Default grants to one-time or session, expire unused grants, stop re-asking after repeated denials |
| 6 | Little Snitch lets the user set a rule lifetime (once, until quit, a period of time, forever), recommends silent mode for new users, lets users preselect alert options, ignores keystrokes for the first second after an alert appears and offers a Research Assistant that explains a connection. | S52 S53 S54 (Doc) | Lifetimes on every grant, a learning period, protection against reflex approval, an "explain this" link |
| 7 | Microsoft Defender Controlled folder access recommends starting in audit mode, protects default system folders that cannot be removed from the list, allows trusted apps one by one and does not trust script engines such as PowerShell by default. | S55 S56 (Doc) | A visible, locked floor. Audit before enforce. Treat shells as untrusted by default |
| 8 | VS Code recommends granting tool and terminal permissions at session level, requires every subcommand of a compound command to match a rule, and warns that rule parsing is best effort with known gaps for aliases and quoting. It states that Assisted permissions are not a security boundary. | S22 (Doc) | Parse compound commands per part. Do not market the risk score as a guarantee |
| 9 | Codex describes auto-review as a change of reviewer, not a permission grant. It advises fixing the sandbox boundary rather than teaching the reviewer to approve noisy escalations. It records recent denials per task. | S17 S67 (Doc) | Keep rules as the boundary and the risk model as the reviewer. If a class of prompt is common, change the rule |

### D2. Patterns that work

1. **Decide by reversibility.** If a checkpoint covers the change, allow and log it. If it cannot be undone from JCVC (network writes, `git push`, deletes outside the project, global installs), ask. [S47]
2. **Three presets with consequences, not mechanics.** Careful, Balanced, Hands off. Each preset lists what it handles and what it asks about, in plain words. (Pattern from S1 S15 S22, language from S47.)
3. **Learning period before enforcement.** Watch mode records what would have been asked for a few sessions, then proposes rules for review. [S53][S55]
4. **Lifetimes on every grant.** Once, this session (default), this project, always. Unused grants expire. [S22][S52][S57]
5. **Examples instead of syntax.** Each rule card shows three example actions it covers and one it does not. The existing "test a command" box becomes "Try it" with the verdict, the rule that decided and the undo path.
6. **Explain every decision.** Allowed by which rule, blocked by which rule, and a safer alternative when blocking. [S14][S22]
7. **Make auto-approvals visible.** A quiet line in the transcript for each auto-allow with a link to the rule. [S22]
8. **Design prompts against habituation.** Distinct visuals per risk tier, highlight the risky part of the command, a short delay before Allow is clickable on high-risk prompts, and batching of similar requests. [S48][S54]
9. **Quiet what the user always answers the same way.** After repeated identical approvals, suggest a rule. After repeated denials, auto-deny with a notice. [S50][S57]
10. **Locked floor shown, not hidden.** A Never list the user can read but not edit, with the reason for each item. [S55]
11. **Rules are the boundary, the model is the reviewer.** Keep the Approver's rules authoritative and use the risk score only to decide between allow and ask inside the rules. [S17][S22]

```
|                                                              |
| Suggestions (2)                                              |
|  You allowed "npm test" 12 times this week.                  |
|  [Handle it in this project] [Everywhere] [Keep asking]      |
|                                                              |
| Recent decisions          [Show all]  [Export audit]         |
+--------------------------------------------------------------+
```

Rule card anatomy

- Plain title ("Install project packages").
- Three covered examples (`npm install`, `pip install -r requirements.txt`, `npm ci`) and one not covered (`npm install -g`).
- Scope (this project or all projects), lifetime (once, this session, until changed, expires after 30 days unused), origin (preset, you, suggestion), last used, Undo.

Decision line templates for the transcript

- "Allowed. Rule Run tests (Balanced). Nothing outside the project changes."
- "Asked you. Pushing code sends it to GitHub and cannot be undone from JCVC."
- "Blocked. Deleting files outside this project is on the Never list. Safer option: delete only the build folder inside the project."

The Advanced view keeps today's rule list, rule packs, YAML editor and insights unchanged.

## E. Progress and feedback during long agent steps

### E1. Research baseline

- Jakob Nielsen's feedback ladder. Under 1 second show nothing. From 1 to 10 seconds show a spinner or skeleton. From 10 seconds to 1 minute show percent done with an honest estimate. From 1 to 10 minutes the user leaves the screen, so status must persist outside it. [S58] These thresholds go back to Nielsen's 1993 work. [S59]
- An indeterminate spinner only says the system is alive. It stops reassuring after about 10 seconds. [S58]

### E2. What the tools do

| Tool | Pattern | Source |
|---|---|---|
| Claude Code CLI | Spinner shows elapsed seconds, streamed token counts and the thinking phase. Third-party scripts rely on the timer as the most reliable busy signal | S60 (User observation) |
| Claude desktop | Session details panel shows where the session runs, what changed, what is running and context use. A tasks pane lists subagents, background shells and workflows. OS notification when a session finishes and you are not viewing it | S1 |
| Copilot cloud agent | Eyes reaction to acknowledge, Started work and Finished work timeline events, PR description updated with status, live session log with Stop session | S26 |
| Zed | Indicators show which tools the model is using while streaming. Follow mode jumps to each file. Notification when the agent waits and a sound when it is done | S40 |
| Codex | Restores elapsed time for in-progress turns after replay, keeps command center rows stable during progress updates, iOS pill to view and stop background commands (22 Oct 2026) | S14 |
| VS Code | When the agent looks idle, check for a pending question, an approval or a still-running terminal command before assuming it hung | S24 |
| Replit | Video replay of the agent's own browser testing | S31 |
| Firebase Studio | Loading status shown in the agent chat and in the preview address bar | S65 |

### E3. Patterns for JCVC

1. **Three explicit states.** Working, Waiting for you, Possibly stuck. Each has its own colour and wording. Waiting for you also fires a Windows notification and the existing phone channels.
2. **Heartbeat age.** Show "last activity 4 s ago" next to the live line. This answers "has it hung" directly.
3. **Determinate progress from the plan.** Use the agent's task list or the approved plan as the measure ("Step 3 of 7, adding the login page"). Do not invent time estimates.
4. **Command output tail.** For installs and builds, show elapsed time and the last output line, with Show output to expand. Count packages when the output allows it.
5. **Big file writes.** Keep the existing characters-so-far counter, add lines so far and the file path, and open the file in the viewer when done.
6. **Startup checklist.** Signing in, loading project, starting preview, ready. Each step ticks off.
7. **Stall rule.** After a configurable period with no output and no pending approval, switch to Possibly stuck and offer Show output, Send a nudge and Stop.
8. **Persistent status outside the window.** Taskbar progress or tray badge if the app shell supports it, plus a toast on finish and on waiting.
9. **One indicator at a time.** Do not stack spinners on progress bars. [S58]
